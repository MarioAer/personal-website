Status: approved

This document specifies the content of the website. Every generating model receives it, together with the build and variant rules in `AGENTS.md`, and every variant links to the version it was built from ("View spec").

## 1. Purpose

A personal website that presents Mario Erazo, an engineering manager and solution architect, and his work in solution architecture, engineering leadership, and AI-assisted engineering. The site is not a CV. It states which problems Mario solves, shows evidence, and makes contact easy.

The same specification is implemented by several AI models, and the visitor can switch between the implementations via a persistent "Built with" selector in the top bar across all viewports. The specification itself is readable from the site. The mechanic is a live demonstration of the third area of expertise (AI-assisted engineering): the same specification, several agents, comparable results.

## 3. Positioning

### 3.1 One-line positioning

Engineering Manager and Solution Architect. Building resilient cloud platforms, leading distributed teams, and engineering workflows for AI agents.

### 3.2 Areas of expertise

Three areas. Each has a name, a one-sentence outcome, four topics, and two or three evidence items. A topic is a generic name of one to three words with a one-sentence description of the work behind it; variants use the topic names as written. Each evidence item is a concise sentence of 10 to 25 words naming a common problem and the resulting outcome. Evidence is true and generic: it describes recurring work, not a single event, and contains no counts, amounts, percentages, company names, client sectors, or tool lists. Variants must present all three areas; order and layout are free.

**Solution architecture and integration**

Outcome: Platforms that remain a single maintainable product while client numbers, external systems, and operational flows scale.

Topics:

- **Platform design.** Cloud infrastructure and container orchestration designed so that client requirements become configurable platform features rather than custom forks.
- **Integration architecture.** Adaptable integration layers decoupling the core platform from diverse client systems across batch files, synchronous APIs, and event streams under mutual security standards.
- **Process mapping.** Translating disparate client operational workflows and external data formats into the platform's core data model to support multi-vendor marketplace flows.
- **Cost architecture.** Consolidating isolated client deployments and dedicated application data stores into shared multi-tenant infrastructure alongside leaner compute, caching, and logging stacks.

Evidence:

- Client systems using disparate protocols connect securely to one core platform without fragmenting the shared codebase.
- Complex external operational workflows and data formats map cleanly into the internal data model without altering core entities.
- Cloud expenditure drops when isolated client environments and dedicated databases are consolidated into shared multi-tenant infrastructure.

**Engineering leadership**

Outcome: Structured delivery, clear technical direction, and predictable releases across distributed engineering teams.

Topics:

- **Workflow design.** End-to-end engineering workflows built from scratch with defined stages and complete visibility across system components and releases.
- **Platform consolidation.** Unifying components, delivery processes, and technical standards across the organisation to reduce active services and operational overhead.
- **Delivery organisation.** Coordinating operations, development, and quality assurance as one unit, turning commercial requirements and security requests into a sequenced roadmap.
- **Cross-team coordination.** Sequencing interface contracts and bidirectional sprint dependencies across internal teams and external contractors in large programmes.

Evidence:

- Distributed teams across operations, development, and quality assurance operate as a unified delivery unit once workflow stages and component tracking are established.
- Fragmented platforms become simpler to operate and faster to deploy once repositories, components, and technical standards are unified.
- Multi-team programmes deliver predictably when interface contracts and mutual sprint dependencies are sequenced upfront across all participating groups.

**AI-assisted engineering**

Outcome: Codebases, observability, and delivery toolchains re-engineered so AI agents execute tasks across the software lifecycle safely.

Topics:

- **Agent-ready codebases.** Consolidating dependent repositories for full visibility, enriched with system-architecture manifests and agent instruction rules.
- **Runtime observability.** Instrumenting application components and logs so AI agents retrieve runtime telemetry for automated verification and debugging.
- **Workflow automation.** Custom integration tooling connecting version control and issue tracking so agents execute commits, merge requests, ticket transitions, and releases.
- **Team enablement.** Establishing guardrails, specifications, and review gates so engineering teams integrate AI agents into daily delivery safely.

Evidence:

- Changes that stall on missing context reach production faster once dependent repositories are merged and documented with architecture manifests.
- Routine delivery overhead shrinks when custom integrations connect version control and issue tracking, enabling agents to automate routine coding workflows.
- Built this website from one specification that several AI models implement independently, allowing direct comparison of their output.

### 3.4 How I work

Nine principles. Each has a generic title of one or two words and a text of one or two sentences, at most 40 words, optimised for scannable web cards or lists; variants use the titles as written. The text is written in the first person.

1. **Context first.** I gather business and technical context first, weigh trade-offs, consult building engineers on an RFC, and record decisions in an ADR.
2. **Peer leadership.** I lead through technical clarity and structured coordination, supporting engineers while keeping delivery moving and adapting to valid counterarguments.
3. **Team alignment.** I conduct technical interviews, hold regular one-to-ones, and align task delegation with platform requirements and individual engineering growth goals.
4. **Shared product.** I evaluate client requests commercially and architecturally, generalizing viable requirements into core features while isolating custom requests behind configuration flags.
5. **Simplicity.** Every separate service, database instance, and repository adds cognitive load. I treat platform consolidation as a concrete deliverable scheduled alongside features.
6. **Documentation.** System-architecture manifests and agent instructions live inside each repository so humans and AI agents see component impact before modifying code.
7. **Measured outcomes.** I evaluate changes by their observable effect on cloud expenditure, lead time from ticket creation to production, and release frequency.
8. **Quality assurance.** Quality is part of the delivery workflow, not an afterthought. I coordinate QA alongside development so changes are verified across all components before release.
9. **Compliance.** Security and compliance requests enter the backlog alongside commercial features, translated into sequenced work packages so mutual standards build naturally into the roadmap.

### 4.2 Content rules

- Neither clients, employers, nor educational institutions are named. Sectors and generic organisation types may be described as written in 4.1.
- Contact data is limited to LinkedIn (`linkedin.com/in/marioaer`) and GitHub (`github.com/MarioAer`). No email address, phone number, postal address, date of birth, photograph, or nationality. The professional facts in 4.1 are permitted.
- No metrics, headcounts, financial amounts, grades, or percentages. Scope and outcomes are described qualitatively. Periods and years in 4.1 are permitted.
- Language: English. Formal register, no contractions, no idioms, no emojis.
- Variants may write their own headlines and connective copy, but every factual statement must trace to sections 3 and 4. Layouts must be optimized for fast scanning by technical leadership.
